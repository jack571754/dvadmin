# 审查补丁：并发边界

`SaveProductSpecView`、普通提报元数据更新、单条删除与批量删除都在 `transaction.atomic()` 内先用 `select_for_update()` 获取工单，再检查是否为本人草稿。批量删除按主键排序获取锁，校验全部目标后再删除。正式提交后的工单不能由这些入口重新打开或删除；普通CRUD也不能写快照或正式提交状态。

支持行锁的数据库（例如PostgreSQL、MySQL/InnoDB）会将同一工单的这些写入串行化，第二个写入在拿到锁后重新检查最新状态。

**SQLite不支持SELECT FOR UPDATE行锁。** 隔离SQLite测试只验证所有入口的草稿/已提交状态规则、权限和事务行为，不证明真实并发提交的行锁互斥。SQLite并发写入还可能返回database is locked；需要严格多写者保证的部署应使用支持行锁的数据库，并在该数据库上运行并发事务验证。本次未新增迁移，未访问真实业务库。
